= Tebako builder images (`tpkg-builder-<triplet>`)

One builder image per (triplet × toolchain family), produced by this one
repo, sha-pinnable, consumed by every slice-producing repo in the tebako
v2 ecosystem (the runtime factory, the feedstocks, the crypto payload) —
and by third-party developers building their own `.tfs` slices with zero
tebako-side toolchain knowledge (TODO.v2-1/13).

The target shape of a slice build — one primitive, identical on a
developer laptop and in GHA (TODO.v2-1/13):

[source,sh]
----
docker run --rm -v $PWD:/w ghcr.io/tamatebako/tpkg-builder-<triplet>@sha256:… tpkg build
# out: <name>-<version>-<triplet>.tfs + payload manifest (+ sha256)
----

(`tpkg build` is the plan's target verb; today the image ships the baked
`tfs` imager, `tebako-pkg`, `tebako`, `tebako-shim` and
`tebako-bootstrap` on PATH, which is what the current feedstock tooling
calls.)

A user of these images needs Docker and nothing else: the toolchain, the
vcpkg dependency trees, the pinned Rust, and the tebako product binaries
are baked image layers.

== The image family

[cols="2,3", options="header"]
|===
| Image (ghcr.io/tamatebako/…) | Base / contract

| `tpkg-builder-x86_64-linux-gnu`
| `ubuntu:20.04` — the glibc 2.31 floor (spec 19 §3), gcc-11 default, clang-19/libclang for bindgen, cmake 3.31.8, patchelf

| `tpkg-builder-aarch64-linux-gnu`
| same, arm64

| `tpkg-builder-x86_64-linux-musl`
| `alpine:3.21` — native musl toolchain, `clang19-libclang` for bindgen, `RUSTFLAGS=-C target-feature=-crt-static` and `VCPKG_FORCE_SYSTEM_BINARIES=1` baked

| `tpkg-builder-aarch64-linux-musl`
| same, arm64
|===

Each triplet is its own registry repository, so every tag is unambiguous
(the v1 images' arch-suffixed tags + manifest step is gone).

.Tags per publish
- `v1.<YYYY.MM.DD>` — dated, immutable by convention
- `v1`, `latest` — moving
- `sha-<shortsha>` — the producing commit

Consumers pin by digest (`…@sha256:…`); the publish workflow prints the
digest of every leg to its run summary.

=== Windows and macOS are runner-native, on purpose

There are no `tpkg-builder-windows-*` / `tpkg-builder-macos-*` images.
GHA cannot run Windows containers that match our native PE/ucrt64 build,
and macOS containers do not exist at all. Their provisioning is already
hermetic in practice (the vcpkg baseline restore + a closed PATH), so
their lever is caching, not containers. This is the documented exception,
not a gap (TODO.v2-1/13 "The model").

== What is baked

* The pinned Rust toolchain (`RUST_VERSION`, currently 1.94.1) with
  clippy + rustfmt, in uid-agnostic homes (`/opt/rustup`, `/opt/cargo`).
* vcpkg at the pinned baseline (`/opt/vcpkg`), with the two installed
  trees as image layers at their canonical absolute paths —
  the image layer *is* the cache; vcpkg trees embed absolute paths, so
  the restore script / manifest-hash tarball / canonical-root map
  machinery of the baseline era does not exist here:
** `/opt/vcpkg-installed/dwarfs/<triplet>` — the dwarfs-t dependency
   closure (boost, openssl, flatbuffers, fmt, …)
** `/opt/vcpkg-installed/sqfs/<triplet>` — squashfs-tools-ng
* The tebako product binaries at the pinned release
  (`tebako-bootstrap`, `tfs`, `tebako-pkg`, `tebako`, `tebako-shim` in
  `/usr/local/bin`) and the product checkout at `/opt/tebako-rs`
  (`tools/stage_link_unit`, the sqfs-sys manifest).
* The dwarfs-rs checkout (with its dwarfs-t submodule) at
  `/opt/dwarfs-rs`.
* The runtime-factory tooling (`tools/build_runtime`) at
  `/opt/tebako-runtime-ruby`, plus the full ruby-build dependency set —
  a factory POSIX leg runs link-unit staging, the ruby build, and image
  packaging inside this one image.
* The environment contract as baked `ENV`:
  `VCPKG_ROOT`, `DWARFS_RS_VCPKG_ROOT`, `DWARFS_RS_VCPKG_INSTALLED_DIR`,
  `DWARFS_RS_VCPKG_TRIPLET`, `SQFS_SYS_VCPKG_INSTALLED_DIR`,
  `SQFS_SYS_VCPKG_TRIPLET`, `CARGO_NET_GIT_FETCH_WITH_CLI=true`,
  `VCPKG_DEFAULT_BINARY_CACHE` — and per family: `LIBCLANG_PATH`,
  `CFLAGS`/`CXXFLAGS=-pthread` (gnu), `RUSTFLAGS`,
  `VCPKG_FORCE_SYSTEM_BINARIES` (musl).

The pins live in link:tpkg-builder/pins.env[`tpkg-builder/pins.env`]
with their upstream owners named; the bake asserts the vcpkg baseline
against `dwarfs-t/vcpkg.json` and fails on drift. The image is
self-describing: the same file is baked at `/opt/tpkg-builder/pins.env`,
and consumer repos match their dwarfs-rs / tebako checkouts to it when
they want a full cache hit (a moved dwarfs-t manifest still builds —
drifted ports rebuild in-leg — just slower).

== Using an image

CI shape (what the feedstock and factory legs collapse to):

[source,sh]
----
docker run --rm -v "$PWD":/w -w /w \
  ghcr.io/tamatebako/tpkg-builder-<triplet>@sha256:<digest> \
  <your build command>
----

Local development: run as your own uid so emitted artifacts do not land
root-owned — the cargo/vcpkg caches are world-writable for exactly this:

[source,sh]
----
docker run --rm -v "$PWD":/w -w /w --user "$(id -u):$(id -g)" \
  ghcr.io/tamatebako/tpkg-builder-<triplet>:v1 \
  <your build command>
----

Notes:

* Inside the musl image, build *without* `--target`: the container's host
  triple is already the musl target, and an explicit `--target` would
  strand host build scripts without the baked `RUSTFLAGS` (the bindgen
  `crt-static` trap — tebako-rs run 30745532174).
* gnu artifacts are gated on needing ≤ GLIBC 2.31 at image build time;
  binaries produced in the image inherit the floor by construction.

== The publish pipeline

link:.github/workflows/publish-builders.yml[`publish-builders.yml`]
builds every leg on its native runner (no qemu on the publish path),
gates the push on the full smoke — toolchain versions, the env contract,
vcpkg baseline parity, `vcpkg list` on both baked trees, the glibc floor
gate, and a probe crate cold-building the heaviest dependency
(`dwarfs-t-sys`) against the baked tree — then pushes and re-verifies the
published digest. A weekly refresh rebuilds with the layer cache busted
so base-image and apt/apk drift is picked up; the pins never float.

Not yet: image signing/verification (cosign) is deferred; consumers pin
digests, and the ecosystem's unsigned-first trust model applies.

== The archived v1 images

The `tebako-ubuntu-20.04` / `tebako-alpine-3.17` Dockerfiles and their
`build-containers.yml` / `add-tag.yml` chain are archived under
link:archive/v1/[`archive/v1/`]. Their published tags remain available;
the runtime factory's container legs keep resolving them until the
consumer rewiring (TODO.v2-1/13 steps 2–3) moves them onto
`tpkg-builder-*`.
